# collection-members

## 0.1.0

The first release. One rule holds a collection whole wherever it sits - the crate, a hex, a domain concept or an adapter - in place of the collection clauses of the `hex-members` rules of nu-hex and adapter-crate. Every pairing is keyed on the directory that holds `collections/` and on the collection, so a crate with several collections or several parts with collections of their own is checked collection by collection; each failing fixture has a whole collection or owner beside the broken one.

It is placed from the product's tastemaker.toml, over the files of the core and of the adapters that hold collections, and not by a spec: it reads the item directories, which are parts of their own, and a rule a spec places does not read the directories of the parts nested in the spec's instance. The `product-*` fixtures use the include globs of that entry, and one failing fixture per level (the core's crate and concept, the adapters' hex and adapter) proves each glob reaches its level.

Clauses, each a finding with its own message and a help that names the `tm workspace scaffold` entry that writes the missing file (`collections`, `collection`, `collection-interface`, `item-module`, `collection-types-test`, `collection-errors-test`, and `part --at <item directory>` for an item's directory):

1. `collections.rs` exists exactly when `collections/` holds a collection (a module file `collections/<c>.rs` or a directory `collections/<c>/`). A collection with no list is reported at each of its files; a list with no collection at the list. That the list declares each collection is `module-declares`'s.
2. Each collection has `interface.rs`, and its module file `collections/<c>.rs` beside its directory; a missing interface is reported at the module file (at each file of the collection when it has no module file either). The files directly in the directory are `.rs` files only: the interface, the optional `interface_test.rs`, `types.rs`, `types_test.rs`, `errors.rs` and `errors_test.rs`, and the item module files; any other file is a finding. An item directory named for one of those six stems is a finding, reported once as that and not also as an item without a module file, because its module file would be the collection's own file.
3. Each collection has an item: an item module file `collections/<c>/<item>.rs` or an item directory. An item module file without its directory `<item>/`, and an item directory without its module file, are findings. What the item's directory holds is the item part's, stated once there: the part spec's counts for kind `item` hold `item.rs` and `item_test.rs` where the product places an item part, and the closed placement refuses an item directory that nothing places, so this rule checks neither file.
4. A collection's `types_test.rs` exists exactly when its `types.rs` has a hand-written trait impl (`impl Trait for Type`), and its `errors_test.rs` exactly when its `errors.rs` has a function body; a test with nothing to prove (or with no `types.rs` or `errors.rs`) is a finding.
5. A collection named for a namespace or a member of the directory that holds it is refused: `steps`, `use_cases`, `adapters`, `inbound`, `outbound`, `domain`, `fixtures`, `factory`, `schemas`, `service`, `interface`, `errors`, `types` or `collections`. The names are the union of the three lists this rule replaces, so none of them loses a name: the hex spec's `hex-core` refused `steps`, `use_cases` and `adapters`; nu-hex's `hex-members` `inbound`, `outbound`, `use_cases`, `domain` and `fixtures`; adapter-crate's `hex-members` `adapters`, `domain`, `fixtures`, `factory`, `schemas`, `service`, `interface`, `errors`, `types` and `collections`.

Read as written: a directory called `collections` is read when a directory holds it, so the files are always under a crate's `src/` and a `collections/` at the very root of the scope has no owner and is not read; the namespace is the one `collections` segment of a path, so a collection called `collections` makes its own directory look like a second namespace and is reported at its own files by the reserved name and by the pairings of that second reading; only `.rs` files are read for a trait impl or a function body, and one written by a macro is not seen.

Fixtures (passing): `crate-collections`, `concept-collection`, `adapter-collection`, `hex-collection`, `product-placement`, `optional-members`, `types-with-impl-and-test`, `errors-with-body-and-test`, `unrelated-files`, `names-near-reserved`. Failing, one per clause or shape: `list-missing`, `list-without-collections`, `module-file-missing`, `interface-missing`, `stray-file-in-collection`, `item-named-for-a-member`, `collection-without-items`, `item-directory-without-module-file`, `item-module-without-directory`, `types-impl-without-test`, `types-test-beside-plain-types`, `types-test-without-types`, `errors-body-without-test`, `errors-test-beside-derived-errors`, `errors-test-without-errors`, one `reserved-<name>` for each of the fourteen names, `product-nu-hex-level-broken`, `product-core-concept-level-broken`, `product-adapters-hex-level-broken`, `product-adapters-adapter-level-broken` and `several-problems`.

a collection's shared cases move from `interface_test.rs` to `fixtures/contract.rs` beside its `fixtures.rs`; the types and errors tests are retired with `types_test.rs` and `errors_test.rs`, so the pairing checks for them are removed and `fixtures` is one of the collection's own members.
