# concept 0.1.2

Places the files of a nested part by their roles, as application-service 0.1.2 does for an operation, where 0.1.1 placed only the concept's own top-level files: a nested part at any depth (`{*part}`) with its `mod.rs` holding its items, its `service.rs`, `types.rs`, `constants.rs`, `errors.rs`, `interface.rs`, `schemas.rs` and `fixtures.rs`, its test support beneath `fixtures/`, its `test.rs` and `service_test.rs`, and its groups of cases `service_test/{*group}/` (`mod.rs`, `test.rs`, `fixtures.rs`); the concept's own test support beneath `fixtures/` and its own groups of cases are placed the same way. Every new entry has `count = { min = 0 }`. Each nested role is placed by its role's own template, as at the top: `errors.rs` by `errors`, `interface.rs` by `interface`, `schemas.rs` by `schemas` with its `schemas_test.rs` by `schemas-test`, and every `test.rs` and `service_test.rs` by `unit-test`; only a nested part's `mod.rs`, which holds its items, is placed by the new spec-local template `part`. The concept's role rules read the nested roles too: each rule that reads `types.rs`, `errors.rs`, `service.rs` or `*_test.rs` at the top also reads the files the matching nested entry places (`{ placed-by = "part-errors" }` and the like), so a file that fails its role cannot pass by moving one directory down. A product's own one-file entry for a nested file writes out more of its path and so places it instead, and the file is read by the role rules once that entry goes. Scenarios `nested-part-is-placed` (nothing closed), `file-of-no-role-in-a-nested-part` (closed), `nested-part-errors-hold-the-errors-role` (a nested errors.rs whose enum is not named for its part is reported by `error-name` and the errors template) and `nested-part-errors-named-for-the-part` (passes). Everything else is as in 0.1.1. 0.1.1 is removed with this version, not kept as published: no lock names it, nothing has been released, and an unreleased version keeps no copy for compatibility.
