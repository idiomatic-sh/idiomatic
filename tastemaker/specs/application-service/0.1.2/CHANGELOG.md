# application-service 0.1.2

Places the files of a nested part by their roles, where 0.1.1 placed only the operation's own top-level files and a product listed each nested file in its manifest. A nested part is a directory at any depth beneath the operation (`{*part}`): its module file `mod.rs`, which holds its items, its `service.rs`, `types.rs`, `constants.rs`, `errors.rs`, `interface.rs`, `schemas.rs` and `fixtures.rs`, its test support beneath `fixtures/`, its `test.rs` and `service_test.rs`, and its groups of cases `service_test/{*group}/` (`mod.rs`, `test.rs`, `fixtures.rs`); the operation's own test support beneath `fixtures/` and its own groups of cases are placed the same way. Every new entry has `count = { min = 0 }`. Each nested role is placed by its role's own template, as at the top: `errors.rs` by `errors`, `interface.rs` by `interface`, `schemas.rs` by `schemas` with its `schemas_test.rs` by `schemas-test`, and every `test.rs` and `service_test.rs` by `unit-test`; only a nested part's `mod.rs`, which holds its items, is placed by the new spec-local template `part`. The operation's role rules read the nested roles too: each rule that reads `types.rs`, `errors.rs`, `service.rs` or `*_test.rs` at the top also reads the files the matching nested entry places (`{ placed-by = "part-errors" }` and the like), so a file that fails its role cannot pass by moving one directory down. A product's own one-file entry for a nested file writes out more of its path and so places it instead, and the file is read by the role rules once that entry goes. Scenarios `nested-part-is-placed` (nothing closed), `file-of-no-role-in-a-nested-part` (closed), `nested-part-errors-hold-the-errors-role` (a nested errors.rs whose enum is not named for its part is reported by `error-name` and the errors template) and `nested-part-errors-named-for-the-part` (passes). Everything else is as in 0.1.1. 0.1.1 is removed with this version, not kept as published: no lock names it, nothing has been released, and an unreleased version keeps no copy for compatibility. A group of the operation's cases, `service_test/{*group}/test.rs` (and a nested part's), is a scenario test placed by `scenario-test@0.1.0` and held by the rule `scenario-test@0.1.0` (`use` lines and at least one `#[test]` function: helpers from fixtures, nothing `pub`), not by `unit-test`'s `CASES` shape, which still holds a test beside its source (`{*part}/test.rs`, `*_test.rs`, `service_test.rs`). A group module is `test-group-module@0.2.0`, held by `test-group-namespace@0.1.0`, so a group that only gathers nested groups is a namespace. Its types follow `public-fields@0.3.0`: a field is at least as visible as its type. Scenarios `group-scenario-test-without-a-test`, `group-scenario-test-exporting-a-helper`, `nested-unit-test-without-cases`, `group-module-holding-a-test` (refused) and `group-namespace-module` (passes). The operation's `service_test.rs` is a case table or the namespace of its groups (only `mod x;` declarations, `test-group-namespace` with `case-table = "exempt"`), placed by `test-group-module@0.2.0`; a group test is `scenario-test`, held to the case-table rules (`test-shape@0.2.0` with `reads = "case-tables"`) when it declares `CASES`.

Edited in place: places `test-shape@0.2.0` with `reads = "every-test"`, `no-runtime-fixtures@0.2.0`, where it named their earlier versions, so a product that places it locks one version of each rule: two versions of one rule share its id, and the earlier entries ran the later query without their params (a `test-shape@0.1.0` entry reported nothing).
