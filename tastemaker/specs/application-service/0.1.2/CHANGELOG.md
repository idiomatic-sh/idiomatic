# application-service 0.1.2

Places the files of a nested part by their roles, where 0.1.1 placed only the operation's own top-level files and a product listed each nested file in its manifest. A nested part is a directory at any depth beneath the operation (`{*part}`): its module file `<part>.rs`, its `service.rs`, `types.rs`, `constants.rs`, `errors.rs`, `interface.rs` and `fixtures.rs`, its test support beneath `fixtures/`, its `service_test.rs`, and its groups of cases (`service_test/<group>.rs`, `service_test/<group>/test.rs`, `fixtures.rs`); the operation's own test support beneath `fixtures/` and its own groups of cases are placed the same way. Every new entry has `count = { min = 0 }`. Each nested role is placed by its role's own template, as at the top, and the operation's role rules read the nested roles too (`{ placed-by = "part-errors" }` and the like), so a file that fails its role cannot pass by moving one directory down. A nested part's module file declares the part's modules only, as the operation's own module file does (`test-group-namespace` with `case-table = "refused"`, entry `part-namespace`): its operation, data and failures go in its role files, held by those roles' rules. Scenarios `nested-part-is-placed` (nothing closed), `file-of-no-role-in-a-nested-part` (closed), `nested-part-module-holding-an-item` and `nested-part-errors-hold-the-errors-role` (refused) and `nested-part-errors-named-for-the-part` (passes).

The operation's `service_test.rs` is a case table or the namespace of its groups, placed by `test-group-module@0.2.0` and held by `test-group-namespace` with `case-table = "exempt"`, which holds a case table to the skeleton the `unit-test` template writes; scenario `service-and-test-of-an-operation` declares it. The spec-local `service-test` template, which nothing places any more, is removed. A group of the operation's cases, `service_test/{*group}/test.rs` (and a nested part's), is a `unit-test` with its own case rows and runners, read by `test-shape` as a test beside its source is; a group module is `test-group-module@0.2.0`, held by `test-group-namespace@0.1.0`, so a group that only gathers nested groups is a namespace. Its types follow `public-fields@0.3.0`. Scenarios `group-test-without-a-table`, `group-test-plain-scenario`, `nested-unit-test-without-cases`, `group-module-holding-a-test` (refused) and `group-namespace-module` (passes). Places `no-runtime-fixtures@0.2.0`, where 0.1.1 named its earlier version, so a product that places it locks one version of the rule. 0.1.1 is removed with this version, not kept as published: no lock names it, nothing has been released.

Edited in place: the module file of a directory is `<dir>.rs` beside it, never `<dir>/mod.rs` (owner, 2026-11-11; `mod_module_files` denied by cargo-workspace 0.13.0). A nested part's module file is `<part>.rs`, placed by the new `idiomatic.arch/part-module@0.1.0`, and a group's is `service_test/<group>.rs`, each at any depth and none of them `mod.rs`. `service_test.rs` and a nested part's `service_test.rs` are placed by the new `idiomatic.arch/service-test@0.1.0` (`kind = "application"`, its scaffold a case table, its doc line 0.1.1's "Behavioral proof of `<operation>` through its injected ports"). A nested part has no `test.rs` (scenario `nested-part-test-is-no-role`, refused) and no `schemas.rs` or `schemas_test.rs`: wire shapes belong to an outbound adapter, admission to the part's `service.rs`.

Edited in place: places `unit-cases@0.2.0`, which reads a namespace `*_test.rs` with the tables of its groups.

Edited in place: the `unit-cases` entry also reads the group tests (`*_test/**/test.rs`), so a namespace `service_test.rs` is judged by its groups' rows (scenario `namespace-service-test-rows-in-its-groups` in concept).

Edited in place: the `unit-cases` entry reads `*_test/**/*.rs` beside its own files, the flat groups and the group directories of a namespace test, which the rule reads only when its entry includes them.

Edited in place: an operation may be a namespace of sub-concepts. The new `namespace` condition, answered by the spec's own rule `namespace-operation`, holds when the operation's directory declares a nested part (`<part>.rs`) and writes no role file of its own (`service.rs`, `service_test.rs`, `types.rs`, `errors.rs`, `constants.rs`, `interface.rs`; a `fixtures.rs` is test support, not a role); then its `service.rs` and its `service_test.rs` are absent (`count = { when = { condition = "namespace" }, then = 0, else = 1 }`), and each part keeps its own service and proof. An operation that writes any role file of its own, or declares no part, still requires both (owner via PM, 2026-11-12: ryo's execution store's `file_dag`). Scenarios `namespace-operation` (passes), `operation-with-neither-service-nor-parts` and `namespace-holding-its-own-types` (service and test reported missing); the rule's own scenarios show the condition's yes and no.

Edited in place: a namespace operation's proofs are held. The spec's own rule `namespace-part-proof` (placed over the operation's own files and every `service.rs` and `service_test.rs` beneath it) reports, in an operation the `namespace` condition holds for, each sub-concept, the topmost part with a `service.rs` on its branch below the namespace, whose `service_test.rs` is not beside its service, and each part of a namespace none of whose parts has a service. A part with no service of its own passes its parts through; a sub-concept's nested parts are proven by its proof, as an operation's are by the operation's; an operation that is not a namespace is not read (leak review of ryo's claude/carveout-v, 2026-11-12: the namespace condition had dropped every proof requirement). Scenarios `namespace-part-with-a-service-and-no-test` and `namespace-of-types-only` (reported), `namespace-operation` (passes); the rule's own scenarios `every-sub-concept-proven`, `operation-is-not-read` (pass), `sub-concept-without-its-test` and `namespace-of-types-only` (reported).
