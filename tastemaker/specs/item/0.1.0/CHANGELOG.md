# item

## 0.1.0

The first version, split from the retired `part` spec by kind. It lists its own files with their counts, shares the templates and rules the other kinds use, and is placed by the crate kind that holds it, so a product's tastemaker.toml names only the crate and its crate kind.

- The item's struct is `<Item>Item` (`JoinItem` implements `OperatorsItem`).
- An item places the `collection` spec at `collections/*`, so a collection that belongs to one item sits inside it (`operators/join/collections/strategies/entity_vector/item.rs`). The engine allows a spec to place a spec that places it only through a `collections/` directory; a spec that places itself at its own path is still refused.
- The fixtures `item-with-nested-collection` and `nested-collection-trait-misnamed` hold that a collection nested in an item is placed with its own name: scaffolding at `.../join/collections/strategies` gives `StrategiesItem`, never the outer collection's.

- **`item-trait`**: a param the collection passes (its own `item-trait`); a collection nested in an item is placed with `absent`. The rule `item-implements-trait` (here, because a collection's rules do not read the files of the item instances nested in it): when the param names a trait, `item.rs` imports that exact path and implements it in an `impl <Trait> for`. The `item` template renders `use <path>;` and `impl <LastSegment> for <Part>Item {}` for a named trait and the `<Collection>Item` of the collection's `interface.rs` for `absent`. Five rule fixtures and the template fixtures `named-trait` and `named-trait-no-impl`.
- An item that holds more than the template's shape (the `tastemaker_placed` item of the `relations` collection: its row and column types, its `constants.rs`, an `impl` with associated types and constants) conforms through the param: its collection names `ryo::languages::ReadItem` (or the engine's own trait) in `item-trait`, so there is no per-collection `interface.rs` for `kind-suffix` and `interface-shape` to read, and the `item` template, which accepts more than it renders, holds the import and the impl.

- **The `item` template reads a pair per collection**: `item-trait` is now a list of `<collection>=<trait path>` pairs (`[]` when no collection names one), a collection with a pair is held to that trait, every other to its own `<Collection>Item`, so a crate whose collections implement different traits is expressible (the language provider: `relations` and `links` implement `ReadItem`, `manifests` implements `ManifestItem`). A new `kernel` param (`kernel`, `provider`, `absent`, threaded from the nu-hex through the concept and the collection like `item-trait`): a kernel crate's item is `pub struct <Part>;` named after its relation, with no `Item` suffix and public, since other crates name it (`pub struct Scope; impl RelationsItem for Scope`); a provider crate's item is `pub(crate) struct <Part>Item;` and the template renders neither the import nor the impl, since the `ryo::reads!` call writes the impl. Template fixtures `kernel-item`, `kernel-suffixed`, `kernel-private`, `provider-macro`, `provider-private`, `other-collections-trait`, `manifest-trait`; the existing ones pass `item_trait = []` or a pair and `kernel = "absent"`.
- **`item-implements-trait` has no param**: an `item.rs` holds a trait impl (`impl <Trait> for`) or a `reads!` / `reads_manifest!` call that names a struct the file declares. The trait itself is held by the template, per collection; the rule holds what the template cannot see, an impl written by a macro. Eight fixtures replace the five: own trait, trait of another crate, kernel naming, `reads!` naming the struct (pass); `reads!` naming another struct, another macro, an inherent impl, a bare struct (violation).
- The nested collections of an item are placed with `item-trait = []` and the item's `kernel`.

- **The `kernel` param is gone, and the item template asks for less** The `item` template renders the collection's own `use super::super::interface::<Collection>Item;` when the collection names no trait of another crate, and nothing else: not the struct, its name, its visibility or the `impl`. A kernel crate names its item after its relation (`Scope`), a feature crate `<Name>Item` and a language provider writes a `reads!` call that implements the trait, and one template cannot say all three, so the rule `item-implements-trait` (an `impl <Trait> for`, or a `reads!` call that names the struct) is what holds an item. The fixtures that expected a finding for a renamed struct, a missing impl or another trait are gone. Two entries cannot place one file with different counts (a count of 0 means the file must be absent), so a variant per role is not possible inside a spec.

- **`test-runners-match-rows`** is placed beside `test-shape`: a test file has a `run(CASES, Word::<word>, subject)` runner exactly for each case word its `CASES` table has rows of. The test templates (`unit-test`, `item-test`, `schemas-test`, `composition-test`, `command-test`, `entry-test`, `use-case-test`, `adapter-test`) no longer render all four runners: an empty table has no runner. The fixtures `*-without-rejects-runner` became `*-with-rejects-row-without-runner`.

Where the collection names the language's `ReadItem`, the `item` template scaffolds a `reads!` call that compiles: it reads every element and says the relation is read only in part (`partial`), because a `row {}` with no column does not compile and a reader that writes nothing and says nothing claims a complete relation. The entries for the item's own collections pass `item-trait` to their templates (`collections`, `collection-module`). The unit test it scaffolds has no `todo!`.
