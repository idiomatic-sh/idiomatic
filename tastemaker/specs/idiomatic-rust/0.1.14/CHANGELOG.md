# idiomatic-rust 0.1.13

`directions-domain` forbids a domain to name the SDK's re-exports of the parse and project traits, `ParseUseCase as Parse` and `ProjectUseCase as Project`, in these spellings: the full path (`ryo::languages::Parse`, imported or written in a signature), the path through the module the house style imports (`use ryo::languages;` then `languages::Parse`), and a glob of the module (`use ryo::languages::*;`), which would bring the traits in unnamed. The patterns are `languages::Parse`, `languages::Project`, `*::languages::Parse`, `*::languages::Project` and `*::languages::\*`. The types beside the traits (`languages::ParseRequest`, `languages::ProjectRequest`, …) and `use ryo::languages;` itself stay open. Not covered: the module under another name (`use ryo::languages as l;` then `l::Parse`). 0.1.12 refuses a use case's `interface` module alias with the pattern `*::inbound::use_cases::*::interface`, which matches the import's target and so refuses the plain import too; here the plain `use ryo::languages;` must stay, and the target is `ryo::languages` whatever name it is bound to, so no pattern can tell the two apart (`*::Parse` and `*::Project` instead gave 98 false positives). No domain uses the alias form today (0 uses). The follow-up is a binding-name check in `import-directions`, a new version of that rule. The trait named bare after a glob is found at the glob itself. The SDK's `ryo::resources::languages::…` spelling is private to the SDK crate and unreachable from a provider. Everything else is as in 0.1.12, which forbids a domain to name a use-case trait by the paths `*::inbound::use_cases::*::interface::*UseCase` and any path ending `UseCase`, the `interface` module itself (`use …::interface as m;`) and a glob of it (`use …::interface::*;`), and `directions-root` forbids a crate's root modules (`src/*.rs`, `main.rs` aside) to name a use-case trait.
