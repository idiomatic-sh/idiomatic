# ci

## 0.2.0

A workflow may start on a pull request and on a push to main, not only by hand: on a public repository GitHub's standard hosted runners are free, so the `check` group, which the pre-commit hook leaves out, runs on every pull request. The workflows' test renames `test_every_workflow_runs_only_when_dispatched` to `test_every_workflow_runs_only_on_its_allowed_triggers` and asserts `trigger_problems(...) == []`: the triggers are a subset of `ALLOWED` (`workflow_dispatch`, `pull_request`, `push`), a `schedule` is allowed only for the workflows `SCHEDULED` names (`benchmarks.yml`), a `push` lists `branches: [main]` alone, and a workflow with a `publish` job or a job in the `release` environment starts by hand alone. Its negative tests refuse a `schedule` elsewhere, `pull_request_target` (it runs a fork's code with the repository's secrets), a push to more than main, and a publishing workflow started by a pull request or a push. The thin-edge test reads a job's `asymptote check --groups ${{ matrix.group }}` with its expression as a group name, so a workflow fans its groups out over a matrix, and lets a check be followed by `actions/upload-artifact` steps alone, which upload what its tools left (a bench's documents). A check may name its product's root, `asymptote check --root <dir> [--groups <groups>]`, so the release runs one product's `release` group. The `workflow-test` rule requires the renamed test.

## 0.1.0

The first release. It is applied at `ci/` and places what CI is beside the workflows: the release job, the workflows' test, and the two checks no command-line tool provides. The workflows under `.github/workflows/` are the `workflows` spec's, applied there, since the repository root's `tastemaker.toml` is open now that a workspace is its whole directory.

Every check is a tool of an `asymptote.toml` (the root's and each product's), in the group `lint`, `perf`, `test` or `release`. `asymptote check` decides what runs, so a workflow only installs the tools and calls it, and the git hook `asymptote init` installs calls it too (`asymptote check --hook pre-commit`).

- `.github/workflows/<workflow>.yml`, a workflow on GitHub Actions, started only by hand (`workflow_dispatch`): a machine, the toolchain, the tools and, for a job that checks, one `asymptote check` call at its end. The `thin-workflow` template holds the name and the trigger; no YAML provider exists, so the rest is held by the test below.
- `ci/workflows_test.py`, the workflows' test (the `workflows-test` template): it reads every workflow with PyYAML and holds it to `workflow_dispatch` as its one trigger and to one `asymptote check [--groups <groups>]` call (run through `cargo bin`, which runs the version the Cargo.toml pins) that ends the job, every other job waiting for a job that checks and running one job command (`ci/<job>/command.py`). The root's `ci-tests` tool runs it, and the `workflow-test` rule requires its two tests, `test_every_workflow_runs_only_when_dispatched` and `test_every_workflow_checks_through_one_asymptote_call`, since the template contract does not compare Python declarations yet.
- `ci/<job>/`, a job that is not a check, today the release: the same small hexagon in Python. `command.py` is the inbound edge (it parses the command line into the use case's `Request`, builds the job through `composition.build()`, runs it, and returns 0, 1 when a step fails, or 2 when the request is `Refused`), `command_test.py` is its intent test over `composition.compose` with every port faked, `composition.py` is `Parts`, `build()` and `compose(parts)`, `use_case.py` and `use_case_test.py` are `Request`, `Refused` and `UseCase` ordering the steps over their ports, `<step>/interface.py` and `interface_test.py` are a step's port and the `conforms` contract, and `<step>/adapters/<adapter>/adapter.py` and `adapter_test.py` are one tool or registry behind the port. A step without an adapter is a finding of the spec's own rule `step-adapter-present`, and a command without `run` and `main` one of `command-entry`.
- `ci/scripts/**`, the scripts: one `script` template whose content is the script's own. Today it is the check with logic no command-line tool provides, which the products' `asymptote.toml` run as `uv run ../../ci/scripts/checks/<name>.py` from the product's directory (`sdk_api.py`: the SDK's public API, its leaks, its recorded listing and its semver break), their tests beside them, the test that a compiling tool's `inputs` reach every path dependency it compiles, and the repository's affected-test and mutation tooling. A script under `ci/` outside `ci/scripts/` is still a finding (`script-beside-the-jobs`).

The spec is closed: a module beside the command and a script under `ci/` outside `ci/scripts/` are findings; a script among the workflows is the `workflows` spec's finding.
