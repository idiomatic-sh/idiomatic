# Ruff benchmark: completed 54-rule baseline

All three pinned project comparisons passed for **54 rules and 1,124 independent cases**, with **108 measured samples** across six alternating-order trials per project. The other **359 shipped defaults were explicitly deferred** at this checkpoint. This is a baseline for continued rule authoring, not full-default parity or the stopping point for implementation.

**The configured lint/check/performance gate failed**, although this benchmark completed. Four other tools failed (core tests/allocation listing, peak, CLI operator catalog, core BDD), and governance reported 12 new findings. Asymptote correctly refused to seed the new benchmark while tool results were unknown. Corrections and broader rule validation are in progress; no unrelated regression was accepted. `correctness.json` preserves all tool outcomes and new findings, with a link to the archived complete gate result.

Cold performance is unacceptable: Django takes approximately **89.8 seconds and 2.73 GiB** in Ryo versus **0.312 seconds and 33.2 MiB** in Ruff. Cached results do not erase this cost.

## Newly discovered annotation boundary

Additional pinned-oracle probes showed that Ruff dispatches LOG001, B002 and B022 inside quoted annotations, including `x: "++value"`; the original candidate missed all three. A generic embedded-expression frontend and an end-to-end planner demand correction now pass a separate **25-case annotation cohort** on worker `7c2d384a0f973117a88e355097c38ebef9f60c06fbb3ea0f7243ee6af1b16014`. The planner regression matters: direct provider fixtures requested child-field metadata explicitly and therefore did not expose the missing demand from semantic-child queries.

A separate ten-case typing-call/context cohort still has four candidate misses. Full shared-harness certification of the migrated query heads is pending. These development cohorts remain distinct from the completed 1,967-case expanded snapshot and the measured 54-rule baseline; none retroactively expands their evidence.

## Profile and engine learning

One separate Django cold profile used the exact measured executable, input fingerprint and 19 findings. Instrumented wall time was 91.647 seconds: reading/evaluation consumed 91,312 ms, compilation 189 ms, listing 1.6 ms. Of 8,914 CPU sample events, `read_row` accounts for 33.11% self time; 31.30 percentage points are below materialization, predominantly through `stream_lookup`. **Five samples were lost** (one reported lost chunk). `profile.json`, `trace.json` and `profile.txt` preserve the evidence; profiling is excluded from the timing samples.

This directly identifies row materialization as a substantial cost. Eager right-side relation materialization, repeated suppression subplans across rules and broad interval joins are follow-on hypotheses to test separately; this profile does not establish their individual contribution or promise a particular speedup. Rule coverage remains the current priority.

The competitor provides concrete design comparisons. At the pinned [Ruff 0.16.5 AST checker](https://github.com/astral-sh/ruff/blob/0.16.5/crates/ruff_linter/src/checkers/ast/mod.rs), rules share a checker that builds semantic context during traversal, with deferred annotation work handled explicitly. Its [lint pipeline](https://github.com/astral-sh/ruff/blob/0.16.5/crates/ruff_linter/src/linter.rs) shares parsed tokens/AST and dispatches categories based on enabled rules, while keeping syntax-error behavior separate from AST checks. Its [cache](https://github.com/astral-sh/ruff/blob/0.16.5/crates/ruff/src/cache.rs) stores per-package diagnostic data with settings/version identity and file modification/permission keys. These observations motivate shared query subplans and demand-driven facts in Ryo; copying cache-key shortcuts without preserving Ryo's correctness guarantees is not a proposed fix.

A separate retained-cache trace reused the exact frozen 54-rule executable, profile, Django inputs and store populated by the cold profile. It returned the same 19 findings in 233.0 ms instrumented wall time: compilation 192.1 ms, listing 4.38 ms and reading 2.47 ms. Compilation accounts for approximately 82% of that observed wall time. This supports investigating reusable compiled plans for retained runs, separately from cold row materialization. Cache-hit counts were not directly instrumented, and no optimization or speedup has been measured. The complete trace events and identity are embedded in `profile.json`.

## Enforced learning

The shared harness refuses unknown/unread candidate relations, missing or extra source files, unequal finding multisets, empty case evidence, unpinned tools and changed certified workload or instrumentation. Compile-fail proofs protect the certificate and publishable sample constructors. Actual collector integration cases exercise CPU, memory, launch failures, stream draining and isolation from a large parent. Positive/negative query cases are colocated with every authored rule and governed by Tastemaker. The configured correctness check runs real reference/candidate cases; the new review adds complete default accounting at that boundary to reject a deleted authored query. The shared entry-boundary test now proves refusal before either contestant executes, and an actual removed-query command mutation also fails as required. These are shared protections inherited by subsequent language benchmarks, rather than documentation-only lessons.

## Default-rule assessment and follow-on work

The measured checkpoint contains **54 corpus-certified rules, 359 explicitly deferred rules, and zero pending rules**. Its frozen-profile comparison has passed. The current development branch expands this to **104 authored rules and 309 deferred rules**; the exact 1,967-case expanded snapshot passed both contestants, followed by 9/9 wildcard regressions. The typing-context misses described above remain unresolved, and the expanded set is not covered by the baseline timings.

The enabled profile remains the complete **413 shipped Ruff 0.16.5 defaults**. Query files are implementations; the `deferred` and `pending` tables account for the rest. `pending` means a bounded syntax implementation is still required. `deferred` means this comparison exposed unavailable facts or query formulations that would require lengthy, fragile duplication. Neither status counts as correctness coverage. The assessment is grounded in upstream tag [`9e4938c4`](https://github.com/astral-sh/ruff/tree/0.16.5/crates/ruff_linter/src/rules), including checker dispatch and helpers, not just rule names.

This table records the capability assessment at the measured 54-rule checkpoint. The expanded development branch is already adding static qualified-name and normalized-identifier facts; its 1,967-case expanded snapshot has passed, while the remaining typing-context gaps await correction and integrated certification. These examples are historical assessment inputs, not a claim that each capability remains wholly unavailable.

The grouped profile explicitly enumerates every affected rule. The following examples are minimal inputs for designing the next implementation; they are not substitutes for each rule's positive, negative, scope, and suppression fixtures.

A separate RyoQL ergonomics issue affects every authored rule: suppression handling repeats a substantial query fragment across all 54 rules. Review-driven work added generic `replace` and `ordered-match` operators, numeric source coordinates and demand-driven indentation regions so these decisions can remain in RyoQL. The corpus also found a concrete B002 error from an inner-operator relation insufficiently constrained to unary nodes; five independent regression cases cover it. Parameterized reusable relations, typed traversal patterns and shared evaluation of common query fragments remain follow-on work. Their potential benefit is reduced repeated scans and materialization; no measured speedup is claimed.

### Additional boundary evidence from implementation

- `execution_context` (PLE1142, PLE1700): `await f()` in a lazy generator body differs from the eager first iterable; an async function's nested synchronous function body differs from its default argument evaluation. PLE1700 must recognize `(yield from xs)` in an async function but exclude nested synchronous bodies and comprehend expression scopes. The persisted 25 oracle fixtures demonstrate these distinctions. Reusable evaluation-region and async-context predicates would avoid duplicating fragile ancestor/body/default/comprehension closures. [Pinned semantic checks](https://github.com/astral-sh/ruff/blob/0.16.5/crates/ruff_python_parser/src/semantic_errors.rs).
- `modernization` (UP026): `mock.mock.patch(); import mock` reports the import only, but reversing those statements also reports the attribute. A function body textually before the import reports the attribute because the checker visits its deferred body after imports. Eight oracle fixtures preserve this behavior. A file-wide import join is incorrect; add generic traversal-phase and module-seen facts or reusable semantic query patterns. [Pinned module-seen check](https://github.com/astral-sh/ruff/blob/0.16.5/crates/ruff_linter/src/rules/pyupgrade/rules/deprecated_mock_import.rs).
- `reference_profile` (PLE0116): the shipped target is Python 3.10; the checker enables this diagnostic only below Python 3.8. `continue` in a loop's `finally` suite produces no default-profile diagnostic but does under `--target-version py37`. The negative default fixture is retained, with no empty query counted as implementation. [Pinned dispatch](https://github.com/astral-sh/ruff/blob/0.16.5/crates/ruff_linter/src/checkers/ast/analyze/statement.rs).
- `upstream_inactive` (F621): the pinned source initializes `starred_index` to `None` and never changes it, so its reporting branch cannot execute. Independent inputs with 255, 256 and 257 targets before `*rest` all produce no Ruff diagnostics. These three negative fixtures preserve the observation; this is an upstream behavior question, not an engine inability or a manufactured no-op implementation. [Pinned starred target check](https://github.com/astral-sh/ruff/blob/0.16.5/crates/ruff_linter/src/rules/pyflakes/rules/starred_expressions.rs).

Other concrete authoring limits found while reducing the pending set: B018 delegates recursive effect detection with builtin identity; PIE790 needs protocol/abstract-method and TYPE_CHECKING contexts; RET501 requires property identity and scoped return/generator analysis; PLE0100/PLE0101/PLE0704 depend on semantic method classification; UP010 needs unused-binding facts and UP029 needs shadowed builtin identity; PLR2044 uses adjacent comment blocks and physical-line context. These are assigned to the existing capability groups rather than represented by partial spelling-based queries.

## Existing Rust replay memory guard

A controlled check of the unchanged Rust replay workload reproduced the 100,000,000-byte warm-peak failure on both untouched `origin/main` (`648ae55e`) and this branch (`8ba81f85`). Three alternating runs of immutable binaries observed 106.79–108.40 MB on the base and 105.29–110.05 MB on the branch. Both ranges exceed the unchanged bound and overlap; this does not establish an introduced memory increase or a speedup. Start/end load averages were 3.4–4.6, so these are failure-attribution observations, not quiet-machine performance claims. Exact bytes and executable identities are retained in `profile.json`. The guard remains failed and unaccepted; a follow-up must attribute compilation high-water versus retained replay allocations and reduce the actual peak without raising the limit.
