# UP034 deferred efficient delimiter pairing

UP034 remains in the existing `modernization` backlog. Raw lossless tokens are
present, so this is not a claim that its syntax is unobservable. The missing
efficient query facility is matching delimiter ownership across arbitrary nested
parentheses, brackets and braces. Current `syntax-child` edges do not supply that
pairing: redundant grouping parentheses are not semantic nodes and can share the
same physical owner with several nested or adjacent pairs.

Full policy needs a matching close for the inner opening, a following outer
close, a nonempty group, and no top-level comma or `yield`. A simplistic adjacent
token or enclosing-expression match cannot establish those conditions. A query
that materializes every preceding token pair to compute depth has quadratic
intermediate work and is intentionally not authored. The bounded follow-up is
generic lossless paired-delimiter metadata, computed with a linear stack scan,
then a rule-local query over those pairs. No parser emulation or engine change
is included here.

Future cases must include `((x))`, nested containers, comments/newlines, empty
tuples, top-level commas and yields, triple grouping, and adjacent call/group
pairs such as `((x)((y)))`. A source-reading prediction about the pinned
reference's destructive token iterator is not an observed discrepancy and must
not be registered as a reference exception without canonical execution.

Policy source:
[`extraneous_parentheses.rs`](https://github.com/astral-sh/ruff/blob/0.16.5/crates/ruff_linter/src/rules/pyupgrade/rules/extraneous_parentheses.rs).
Current fact audit: Python `domain/extras/types.rs`, syntax-child
adapter, and the generic `ordered-match` contract (earliest later match rather
than a stack of paired delimiters). This note does not count as authored coverage.
