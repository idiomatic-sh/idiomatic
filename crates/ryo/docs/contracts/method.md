## 2. Rubric

Each row is **execution route × resource family/representation**. Enumerate actual registry, acquire/select, publication/Selected constructors, cache accesses and terminal drivers; map every resolved site exactly once. Unmapped sites block closure.

Tastemaker enforces imports, layout, required assets and structural access. Its descriptive orchestration rules do not yet enumerate and reject every non-readable flow bypass; that structural gate remains open. Runtime tests establish behavior, completeness, lifetime and performance that structural rules cannot observe. Apply the [systemic audit workflow](../../../../.agents/skills/systemic-audit/SKILL.md) to repeated findings before closing a matrix row.

| Question | Ownership axes to prove | Required evidence |
| --- | --- | --- |
| Q1 Who may prepare, admit, build, publish and execute; in which phase? | Scheduling, sharing, invalidation, data, lifetime | Actual callers; Tastemaker structural access; runtime admission and failure controls. |
| Q2 At what frequency does work repeat: request, file/population, rule, node, row? | Scheduling, sharing | Cross-rule consumers, build counts and actual reached workload counts. |
| Q3 Which cardinalities, join order, bindings, indexes, scans, materializations and recursive deltas drive work? | Scheduling, data | Input/fanout distributions; preserved native/bulk paths; counted route costs. |
| Q4 Who owns required versus optional bytes, aliases, metadata and release? | Sharing, data, lifetime | Single backing charge; zero-budget sharing; last-consumer, refusal and error release. |
| Q5 Are diagnostics, coverage, ordered bags, partial absence, lazy errors and emitted prefixes preserved? | Scheduling, invalidation, lifetime | Competing-error, empty-input, partial/recovery and downstream-refusal controls. |
| Q6 What identifies and invalidates a population/view/result? | Sharing, invalidation | Generations, bindings, ordered projections/positions, same-buffer refill and dependency controls. |
| Q7 What is shared versus worker-local, and what workload/mode was measured? | Scheduling, data, lifetime | Determinism, aggregate peak, language/corpus/rules/threads and separate cold/warm/edit receipts. |

Cells are **proven: test/receipt**, **falsified: file:line**, or **unknown**; any falsified authority leaves its ownership checkbox unchecked. Traits/registry coverage alone prove neither sole ownership nor speed. Q2–Q4 workload-cost claims require attributable counted diagnostics or frozen-workload receipts; synthetic tests prove only their constructed mechanism. Shared untagged counters cannot identify a route. Exercise all 26 operation kinds, including the 25 public query operators, through actual DAG/root and residual/terminal routes; compile positives must use real capability types before negatives.

## 4. How to work

- [ ] Identify the semantic interface, engine-owned policy/state/lifetime, every implementation and actual route before changing code.
- [ ] Run a short isolated POC: hypothesis, smallest representative workload, baseline plus counts; document temporary contract debt, with no checked ownership credit.
- [ ] Consolidate into one production owner; remove replaced paths and preserve native access and lazy/error semantics. Use Tastemaker for structural boundaries and runtime tests for behavior and lifetime.
- [ ] Investigate first regressions using preserved baseline/failure receipts and route coverage; iterate the systemic migration instead of automatically abandoning it or raising caps.
- [ ] Invest in the shared benchmark harness: inventory, enumeration, execution, normalization, comparison, reporting and performance belong there; linters supply config/query/cases and necessary protocol adapters only, with no hardcoded rule exceptions.
- [ ] Repeat independent Fable review and fixes until blockers close; then run Rust/Python correctness and frozen cold/warm/edit performance gates before acceptance.

Build targets. Each worktree builds into its own cargo target, `idiomatic-target/<worktree name>` in the workspace mount, and `.claude/hooks/guard_shell.py` refuses any other `--target-dir` for a build, test, bench, clippy or run, another tree's name included; builders' `cargo check` keeps the check-only target, `idiomatic-check-target/<worktree name>`. Cargo judges freshness by source mtimes, so a target shared across worktrees served validation327's `core_bdd` and `core_allocation` dependency units another tree had built with a debug print. The shared `idiomatic-benchmark-guards/target` is accepted, with a deprecation message, only for the `ryo-perf-*` measurement trees that already use it, and is removed when the heap-profiling measurement running on it is done. Deleting a worktree deletes its target directory by its exact path in the same turn.

Measurement requests. Every perf and receipt request stages its rules, query fragments and `benchmark.toml` from the measured source tree, the commit its worker is built from, and never from a `/tmp` copy, an earlier request or a hand-patched one: at 321 and 323 the full-Django request read a rule copy staged on 2026-11-05, and three rules were Unknown everywhere by queries the tree no longer had. The one staging command is `python3 -I crates/ryo/languages/python/benchmarks/linters/ruff/verify_profiles.py --stage-request <pinned request> --source <measured commit> --output-dir <fresh directory>`. It takes the corpus side (root, files, context manifest) from the pinned request, extracts `rules`, `fragments` and `benchmark.toml` at the measured commit with `git archive`, reads every rule-side field of the request (selected rules, applicability, query modules, observations, rule context, parser configuration, project context) from that staged `benchmark.toml`, and writes `request.json` and `staged.json`. It prints the staged digest: the sha256 of the lines `<sha256>  <path>` of every staged file, in path order. The receipt records that digest and the measured commit beside the worker's sha256; a receipt without them is not a measurement of that source.

Heap profile. Every perf iteration that reports memory takes the same heap profile, with jemalloc's own profiler and its `jeprof`, on the allocator the worker ships with. heaptrack cannot be used: it intercepts `malloc`, so it sees none of jemalloc's prefixed `_rjem_` calls; and on a system-allocator build its `heaptrack_interpret` grows from 0.2 GB to over 40 GB within about 40 s while 77% of its time is one probe loop of its allocation-info hash set (keyed on size and trace), and is OOM-killed (exit 137, the cgroup `oom_kill` count rises), so the recording stops there, recorded raw (`-r`) and interpreted afterwards the same; heaptrack 1.5.0 has no setting that changes this. Build the worker with the profiler and line tables from a per-tree target, under the lock, and copy it and `jeprof` out under the same lock: `flock <the build lock> sh -c 'CARGO_PROFILE_BENCH_DEBUG=line-tables-only cargo bench --no-run -p idiomatic-sh-ryo-python --bench ruff --features heap-profile --target-dir <per-tree target> --locked --offline --message-format=json > <out>/build.json && cp <the ruff executable named in build.json> <out>/worker && cp <per-tree target>/release/build/tikv-jemalloc-sys-*/out/build/bin/jeprof <out>/jeprof'`, then record `sha256sum <out>/worker` and the commit. Stage the request (above) and run it cold, under the lock: `_RJEM_MALLOC_CONF=prof:true,prof_active:true,lg_prof_sample:19,lg_prof_interval:32,prof_final:true,prof_prefix:<out>/prof/jeprof /usr/bin/time <out>/worker run-ryo --request-file <request.json> python-target=3.10`; it samples one allocation per 512 KiB and dumps the live heap every 4 GiB allocated (611 dumps, 99 MB, for full Django 413; 379 s against the 327 receipt's 322.7 s, the same 6.8 GB peak RSS and byte-identical output). The dump whose `perl <out>/jeprof --text --show_bytes <out>/worker <dump>` total is largest is the peak, and the totals in dump order show how it builds; read the peak with `perl <out>/jeprof --text --cum --show_bytes --lines --nodecount=400 <out>/worker <dump>` (bytes live by source line), split it with `--focus=<function>` / `--ignore=<function>`, and compare two dumps with `--base=<earlier dump>`. `prof_gdump` (a dump at every new high-water mark) is not used: one file writes 30,000 dumps. The `heap-profile` feature reaches only the Python crate's dev-dependency allocator, so no release build takes it.
