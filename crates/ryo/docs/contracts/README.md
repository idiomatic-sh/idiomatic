## 4. How to work

- [ ] Identify the semantic interface, engine-owned policy/state/lifetime, every implementation and actual route before changing code.
- [ ] Run a short isolated POC: hypothesis, smallest representative workload, baseline plus counts; document temporary contract debt, with no checked ownership credit.
- [ ] Consolidate into one production owner; remove replaced paths and preserve native access and lazy/error semantics. Use Tastemaker for structural boundaries and runtime tests for behavior and lifetime.
- [ ] Investigate first regressions using preserved baseline/failure receipts and route coverage; iterate the systemic migration instead of automatically abandoning it or raising caps.
- [ ] Invest in the shared benchmark harness: inventory, enumeration, execution, normalization, comparison, reporting and performance belong there; linters supply config/query/cases and necessary protocol adapters only, with no hardcoded rule exceptions.
- [ ] Repeat independent Fable review and fixes until blockers close; then run Rust/Python correctness and frozen cold/warm/edit performance gates before acceptance.

Boundary decision: keep strong semantic crates with mandatory typed contracts. Share stable borrowed views or typed handles across them; the common application engine owns buffers, acquisition, invalidation and lifetimes. Change representation where measured copying, materialization or index builds warrant it. Historical consolidation into core to avoid conversions is not a reason to collapse crates for speed, and the older crate layout is design input rather than a restoration target. Strategy selection is still an open rail: replace engine environment reads with typed request choices that also bind stored-result identity and benchmark receipts; distinct retention, digest and column choices must be recorded without inventing separate execution pipelines.

The [reviewed execution direction](evidence/execution-redesign-plan-20261104.json) is a plan, with no implementation or ownership credit: `prepare(request)` → `open_run` → `plan_reuse` → `visit_files` → `finish_project` → `finish_run`. One application-owned executable program must carry a typed `Partition`, ordered `DemandProgram`, owner-issued `AdmittedInput` and required input admission. Every physical route must preserve its lazy demand, error order, observation readiness, publication identity and last-use release.
